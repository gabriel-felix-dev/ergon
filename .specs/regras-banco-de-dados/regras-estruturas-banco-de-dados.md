# Regras para a estrutura de pastas e arquivos do banco de dados

Este documento define as regras que agentes de IA devem seguir ao criar ou alterar arquivos do banco de dados do projeto Ergon.

## Estrutura de pastas

Salvar os arquivos conforme sua finalidade:

```text
data-base/
├── script/  # Scripts gerais de criação e configuração do banco
├── trg/     # Triggers
├── fnc/     # Functions
├── sp/      # Stored procedures
└── vw/      # Views
```

## Scripts gerais

- Salvar scripts gerais na pasta `data-base/script/`.
- Usar `kebab-case` no nome do arquivo: letras minúsculas e palavras separadas por hífen.
- Exemplo: `script-ergon.sql`.

## Arquivos SQL (PostgreSQL)

Salvar cada arquivo na pasta correspondente ao tipo do objeto. O nome deve começar pela sigla do tipo em maiúsculas, seguida de `_` e do nome da finalidade em PascalCase. Usar a extensão `.sql`.

| Tipo | Pasta | Padrão | Exemplo |
| --- | --- | --- | --- |
| Function | `data-base/fnc/` | `FNC_NomeDaFuncao.sql` | `FNC_QuantidadeOrdemServico.sql` |
| Trigger | `data-base/trg/` | `TRG_NomeDaTrigger.sql` | `TRG_AtualizaOrcamentoAposRecusaDoCliente.sql` |
| Stored procedure | `data-base/sp/` | `SP_NomeDaProcedure.sql` | `SP_CadastraAssistenciaTecnica.sql` |
| View | `data-base/vw/` | `VW_NomeDaView.sql` | `VW_GerentesAssistenciasTecnicas.sql` |

### Regras de nomenclatura dos arquivos SQL

- Manter a sigla do tipo em maiúsculas: `FNC`, `TRG`, `SP` ou `VW`.
- Separar a sigla do nome com um único sublinhado (`_`).
- Escrever o nome após o sublinhado em PascalCase, sem espaços, hífens ou acentos.
- Descrever no nome a finalidade do objeto.
- Usar a extensão `.sql` em todos os arquivos SQL.

## Documentação dentro do código

Os arquivos SQL deverão seguir um padrão rígido de documentação dentro do próprio código. **A formartação dos arquivos de ser rígidamente seguida**. É importante que seja bem descrito o objetivo e que sejá comentado as lógicas presentes dentro código para que qualquer pessoa possa entender.

## Performance

Tenha como premissa **POUPAR O BANCO**. Sempre analise a melhor estruturas para que os processos de execução do banco de dados sejam os mais performáticos possível.

### Transactions e tratamento de exceções

No PostgreSQL, cada comando executado fora de uma transação explícita é confirmado automaticamente se tiver sucesso. Quando uma operação do sistema envolve vários comandos que precisam funcionar como uma unidade, a aplicação/chamador deve abrir uma transação, confirmá-la com `COMMIT` quando tudo der certo ou cancelá-la com `ROLLBACK` se algum passo falhar.

`BEGIN;` como comando SQL inicia uma transação. Já `BEGIN ... END` dentro de um bloco PL/pgSQL delimita um bloco de código e, sozinho, não inicia uma transação.

```sql
BEGIN;

UPDATE public."Tabela"
    SET "Coluna" = 'Valor'
    WHERE "Id" = 1;

-- Executar aqui os demais comandos da mesma operação.
-- Se todos tiverem sucesso, confirmar:
COMMIT;
-- Se algum falhar, executar ROLLBACK em vez de COMMIT.
```

Se um comando falhar dentro de uma transação explícita, a transação fica em estado de erro. O chamador deve executar `ROLLBACK` (ou voltar a um `SAVEPOINT`) antes de continuar. A aplicação deve tratar uma exceção ou um código de erro como falha da operação e não confirmar a transação.

Em PL/pgSQL, use blocos `EXCEPTION` quando for necessário tratar um erro ou convertê-lo em um código de retorno. Quando uma exceção é capturada, as alterações feitas no bloco protegido são revertidas automaticamente. Se o erro não deve ser convertido em um resultado de negócio, propague-o com `RAISE;` para que o chamador possa cancelar a transação.

```sql
-- Trecho ilustrativo dentro de uma rotina PL/pgSQL:
BEGIN
    -- Executar aqui os comandos que pertencem ao bloco protegido.
    UPDATE public."Tabela"
        SET "Coluna" = 'Valor'
        WHERE "Id" = 1;

EXCEPTION
    WHEN OTHERS THEN
        -- Repropaga o erro; o chamador deve tratar e cancelar
        -- a transação explícita, se houver uma.
        RAISE;
END;
```

Use o padrão de códigos negativos definido para procedures quando a rotina precisar devolver um resultado de erro em vez de propagar a exceção. Nesse caso, a aplicação deve verificar o código: **0** significa sucesso; código negativo significa falha e não deve ser confirmado como sucesso. O bloco `EXCEPTION` reverte as alterações realizadas dentro do bloco protegido antes de devolver o código.

Não execute `ROLLBACK` manualmente dentro de functions ou trigger functions. Triggers fazem parte da instrução que os disparou: use `RAISE EXCEPTION` para cancelar essa instrução ou retorne `NEW`, `OLD` ou `NULL` conforme o comportamento do trigger. Procedures só podem controlar transações com `COMMIT`/`ROLLBACK` quando chamadas por `CALL` no nível superior e sem um bloco de transação explícito ou comandos intermediários; por padrão, deixe a aplicação/chamador controlar a transação.

### Procedure

```sql
CREATE OR REPLACE PROCEDURE public."SP_NomeDaProcedure"(
    IN "Parametro" VARCHAR(100) DEFAULT NULL,
    INOUT "Retorno" INTEGER DEFAULT 0
)
LANGUAGE plpgsql
AS $$
    /*
    Documentacao
    Arquivo Fonte............: SP_NomeDaProcedure.sql
    Objetivo.................: Objetivo da SP
    Autor....................: nome de quem criou
    Data.....................: data de criação
    Ex.......................: CALL public."SP_NomeDaProcedure"('%Valor%', 0)

    Retornos.................:  0 - Sucesso
                               -1 - Erro: ...
                               -2 - ...
                                .
                                .
                                .
    */
BEGIN
    -- Lógica da procedure
    "Retorno" := 0;

EXCEPTION
    WHEN OTHERS THEN
        "Retorno" := -1;
END;
$$;
```

Use códigos negativos em `PROCEDURES` que executem comandos de `INSERT`, `UPDATE` ou `DELETE` e somente **0** para sucesso. No PostgreSQL, use parâmetros `OUT` ou `INOUT` para devolver esses códigos; a chamada da procedure é feita com `CALL`. Quando um código negativo for devolvido após uma exceção tratada, as alterações do bloco protegido já terão sido revertidas; a aplicação deve reconhecer esse retorno como falha e não confirmar a operação.

### Function (tanto escalar como tabular)

```sql
CREATE OR REPLACE FUNCTION public."FNC_NomeDaFuncao"("Parametro" INTEGER)
RETURNS INTEGER
LANGUAGE plpgsql
AS $$
    /*
    Documentacao
    Arquivo Fonte............: FNC_NomeDaFuncao.sql
    Objetivo.................: Objetivo da FUNC
    Autor....................: Nome de quem criou
    Data.....................: data de criação
    Ex.......................: SELECT public."FNC_NomeDaFuncao"(1) AS Resultado;
    Retornos.................: 0 - Sucesso
                               1 - Erro:
                               2 - ...
                               .
                               .
                               .
    */
BEGIN
    -- Lógica da função
    RETURN 0;

EXCEPTION
    WHEN OTHERS THEN
        RETURN 1;
END;
$$;
```

Para funções tabulares, declarar um tipo de retorno compatível, como `RETURNS TABLE (...)` ou `RETURNS SETOF ...`.

### Triggers

No PostgreSQL, a lógica de um trigger é implementada em uma function sem argumentos que retorna `trigger`; o trigger é declarado separadamente. Use `BEFORE` ou `AFTER` para tabelas. `INSTEAD OF` é usado em views e deve ser row-level (`FOR EACH ROW`).

```sql
CREATE OR REPLACE FUNCTION public."TRG_NomeDaTrigger"()
    RETURNS trigger
    LANGUAGE plpgsql
    AS $$
        /*
        Documentacao
        Arquivo Fonte............: TRG_NomeDaTrigger.sql
        Objetivo.................: Objetivo da TRG
        Autor....................: Nome de quem criou
        Data.....................: data de criação
        */
    BEGIN
        -- Lógica do trigger
        IF TG_OP = 'DELETE' THEN
            RETURN OLD;
        END IF;
        RETURN NEW;
    END;
$$;

DROP TRIGGER IF EXISTS "TRG_NomeDaTrigger" ON public."NomeTabela";

CREATE TRIGGER "TRG_NomeDaTrigger"
    BEFORE INSERT OR UPDATE OR DELETE ON public."NomeTabela"
    FOR EACH ROW
    EXECUTE FUNCTION public."TRG_NomeDaTrigger"();
```

## Instrução para agentes de IA

Antes de criar ou alterar um arquivo do banco de dados, identificar o tipo do arquivo, salvá-lo na pasta correspondente e conferir se o nome segue as regras acima. Preservar o padrão de documentação definido pelo responsável pelo projeto quando ele estiver disponível.
